# 召回测试实验操作手册

> 适用对象：问数平台 Schema 向量召回（表 / 字段 / 指标）  
> 前置条件：元数据已同步到 L1，向量索引已构建（Qdrant `wenshu_knowledge`）  
> 相关入口：平台「召回测试」页、`POST /api/search/test`

本文说明三件事：

1. **怎么做**：从准备环境到出报告的完整步骤  
2. **怎么设计实验内容**：黄金集怎么出题、怎么标注  
3. **怎么看召回**：UI / 指标 / 失败 case 怎么读、怎么决策

## 0. 先搞清：这里的「召回」评什么

问数链路是：

```text
自然语言问题 → 向量召回相关表/字段 → 拼 M-Schema → LLM 生成 SQL → 沙箱执行
```

**本实验只评第一步「召回」**，不评 SQL 对不对。

| 算召回成功 | 不算本实验范围 |
|------------|----------------|
| 该用的表进了 Top-K | SQL 语法 / 执行结果 |
| 关键过滤/聚合字段能找到 | 权限、脱敏、追问策略 |
| 排序大致合理（正确表靠前） | 端到端答案正确率 |

PRD 目标（离线黄金集）：

| 指标 | MVP | v1.0 |
|------|-----|------|
| 表召回命中率 | ≥ 80% | ≥ 90% |

本手册默认用：**表级 Hit@10 ≥ 80%** 作为 MVP 门槛。

## 1. 实验怎么做（按顺序执行）

### 1.1 准备工作清单

在开始出题 / 跑批前，确认：

| # | 检查项 | 怎么确认 |
|---|--------|----------|
| 1 | 原始库、元数据库、向量库已连接 | 平台「连接配置」 |
| 2 | L1 有启用表（`is_enabled=1`） | 元数据编辑 / 同步页 |
| 3 | 向量集合已建且有点数 | 「向量库同步」完成；或查 Qdrant points_count |
| 4 | 平台「召回测试」能出结果 | 输入一句业务话，点「测试检索」 |
| 5 | 冻结一版索引快照信息 | 记下日期、表数量、points_count、embedding 模型 |

建议在报告头固定记录：

```text
评测日期：
embedding：Qwen3-Embedding-0.6B
collection：wenshu_knowledge
points_count：
启用表数：
库范围：仅当前原始库 / 全部已索引库
Top-K：5 / 10 / 15 / 30
```

> 不冻结环境，后面改了注释或重跑索引，指标无法对比。

### 1.2 推荐实验节奏（5 天）

| 天 | 做什么 | 产出 |
|----|--------|------|
| D1 | 定核心表白名单（建议 15–30 张）；写 20 道单表 + 易混淆题 | 初版黄金集半稿 |
| D2 | 补到约 50 题；两人互审标注 | `evals/golden/recall_v1.jsonl` |
| D3 | 跑 baseline（纯向量，K=5/10/15/30） | E0 报告 + 失败清单 |
| D4 | 按失败原因改 description / 同义词，再复测 | E3/E4 对比表 |
| D5 | 定是否达标；把回归步骤写进日常 | 决策结论 + 复测约定 |

### 1.3 两种执行方式

#### 方式 A：人工肉眼测（先熟悉「怎么看」）

1. 打开平台 → **召回测试**
2. 勾选「仅当前原始库」（与线上默认一致）
3. 输入黄金集里的 `question`
4. 点 **测试检索**
5. 看返回列表：类型（table/column/metric…）、表名、字段名、score
6. 对照该题的 `must_tables` / `must_columns`，在表格里打勾

适合：先测 10 题，统一标注口径；或排查单题失败。

#### 方式 B：批量脚本（正式出指标）

建议目录：

```text
evals/
  golden/recall_v1.jsonl
  scripts/run_recall_eval.py
  reports/recall_E0_YYYYMMDD.md
```

脚本逻辑（与线上一致）：

```text
对每题 question：
  embed(question) → search_collection(limit=K, db 过滤同线上)
  取 hits 中的 table / column
  判断 must_tables / must_columns 是否被覆盖
汇总 Hit@K、MRR、按题型切片、导出失败 case
```

也可先用接口手测 / 脚本调同一路径：

```http
POST /api/search/test
{
  "query": "年龄大于30的个人客户有多少",
  "limit": 15,
  "all_databases": false
}
```

### 1.4 实验矩阵（一次只改一个变量）

| 实验 ID | 改什么 | 目的 |
|---------|--------|------|
| **E0** | 纯向量，limit=15，仅当前库 | 现状摸底（baseline） |
| **E1** | limit = 5 / 10 / 15 / 30 | 找「够用的最小 K」 |
| **E2** | 仅当前库 vs 全部已索引库 | 库过滤是否伤召回 |
| **E3** | 补全表/字段 description 后再索引 | 验证元数据质量 ROI |

**纪律**：对比 E0 时，黄金集不变、模型不变；只改表中那一列变量。

1. 填汇总表（见 §3.2）  
2. 导出失败题清单，打失败原因标签（见 §3.3）  
3. 写一句决策：达标 / 不达标；下一步改元数据还是改检索

## 2. 怎么设计实验内容（黄金集）

### 2.1 设计原则

1. **按「能写出正确 SQL 的最小 schema」标注**，不要把语义沾边的表都标成 must  
2. **一题 must 表不超过 2–3 张**，避免标注过宽导致指标虚高  
3. **覆盖真实业务问法**，不要只写字段中文名的直译  
4. **故意出易混淆题**（个人 vs 对公、用信 vs 授信、计划 vs 明细）  
5. **正负例分开算**：负例（不该乱召）不计入 Hit@K 主指标

### 2.2 题型配额（建议共 50 题）

| 类型 | 题数 | 测什么 | 示例问法 |
|------|------|--------|----------|
| 单表过滤 / 聚合 | 12 | 基础语义 | 「年龄大于 30 的个人客户有多少」 |
| 易混淆表 | 8 | 边界是否写清 | 「对公客户数量」勿召到个人客户表 |
| 多表 JOIN | 10 | 多对象同进 Top-K | 「某客户的用信申请金额」 |
| 业务黑话 / 同义词 | 8 | 别名与口语 | 「用信」「放款」「vintage」「迁徙率」 |
| 指标 / 口径 | 6 | 优先指标或 APP 宽表 | 「在贷余额」「通过率」 |
| 负例 / 拒答 | 6 | 不该乱召 | 无关主题、写操作、无表可答 |

正例约 44 题用于 Hit@K；负例 6 题单独看「污染 / 乱召」。

### 2.3 每题必须标注的字段

推荐 JSONL，一行一题：

```json
{
  "id": "Q012",
  "question": "年龄大于30的个人客户有多少",
  "domain": "客户",
  "difficulty": "easy",
  "tags": ["单表", "过滤", "聚合"],
  "must_tables": ["DWD_IP_INDV_CUST_INFO"],
  "nice_tables": [],
  "must_columns": [
    {"table": "DWD_IP_INDV_CUST_INFO", "column": "age"},
    {"table": "DWD_IP_INDV_CUST_INFO", "column": "cust_id"}
  ],
  "forbidden_tables": ["DWD_IP_CORP_CUST_INFO"],
  "notes": "个人客户；勿召到对公客户表"
}
```

| 字段 | 含义 | 判定 |
|------|------|------|
| `must_tables` | 写 SQL 必不可少的表 | 缺任一表 → 该题表召回失败 |
| `nice_tables` | 有更好、没有也能答 | 命中加分，不算失败 |
| `must_columns` | 过滤/聚合/关联真正用到的列 | 字段 Hit 用；MVP 可先只盯表 |
| `forbidden_tables` | 明显错表 | 进 Top-K 记「负向污染」 |
| `tags` | 题型切片 | 出分题型报告用 |

### 2.4 出题步骤（实操）

**Step 1：定核心表白名单**

从当前已索引、业务常问的表里选 15–30 张，例如（按你们 `sql/raw` 可调整）：

- 客户：`DWD_IP_INDV_CUST_INFO`、`DWD_IP_CORP_CUST_INFO`
- 申请 / 用信：`DWD_EV_INDV_LOAN_APP`、`DWD_EV_INDV_CRD_APP`
- 借据 / 还款：`DWD_AR_LOAN_INFO`、`DWD_EV_REPAY_PLAN`、`DWD_EV_REPAY_DETAIL`、`DWD_EV_OVERDUE_REPAY`
- 产品 / 宽表：`DWD_PRD_INFO`、部分 `APP_*` / `DWS_*`

只对这些表出题，避免「库里有上千表但题只覆盖 3 张」导致指标不可信。

**Step 2：每张核心表至少 1～2 道「直球题」**

用表注释 / 字段注释里的业务词提问，例如：

- 表：个人客户信息 → 「个人客户的年龄和学历分布」
- 字段：`app_loan_amt` 申请用信额度 → 「用信申请金额汇总」

**Step 3：专门写「易混淆对」**

| 问法偏向 | must | forbidden |
|----------|------|-----------|
| 个人客户… | `DWD_IP_INDV_CUST_INFO` | `DWD_IP_CORP_CUST_INFO` |
| 对公 / 企业客户… | `DWD_IP_CORP_CUST_INFO` | `DWD_IP_INDV_CUST_INFO` |
| 用信申请… | `DWD_EV_INDV_LOAN_APP` | 授信申请表（若存在） |
| 还款计划… | `DWD_EV_REPAY_PLAN` | `DWD_EV_REPAY_DETAIL` |
| 逾期还款… | `DWD_EV_OVERDUE_REPAY` | 普通还款明细 |

**Step 4：同义改写**

同一意图写 2 种问法，例如：

- 「年龄大于 30 的个人客户有多少」
- 「自然人客户里，满 30 周岁的人数」

用来测：描述/同义词是否覆盖口语，而不是只匹配书面注释。

**Step 5：互审**

第二人只看 question，先自己想该用哪张表，再对标注；不一致就讨论，以「最小可写 SQL」为准。

### 2.5 难度建议

| difficulty | 含义 |
|------------|------|
| `easy` | 问法接近表/字段中文注释 |
| `medium` | 需要同义词或区分相近表 |
| `hard` | 多表、指标口径、或业务黑话 |

MVP 不必追求 hard 很多；**easy+medium 达标比 hard 堆题更重要**。

## 3. 怎么看召回（读结果）

### 3.1 在平台 UI 上怎么看

打开 **召回测试**，输入问题后关注：

```text
检索范围：当前库 xxx
命中 N 条
┌─────────────────────────────────────────┐
│ score  type    table              column │
│ 0.82   column  DWD_IP_INDV_...    age    │
│ 0.79   table   DWD_IP_INDV_...           │
│ 0.71   column  DWD_IP_CORP_...    age    │  ← 可能是污染
└─────────────────────────────────────────┘
```

**人工判定口诀：**

1. **先看表**：`must_tables` 有没有出现在列表里（不要求第一名，但最好进 Top-10）  
2. **再看位次**：正确表是第几条？越靠前越好（关系到 prompt 截断）  
3. **再看字段**：过滤/分组字段是否出现；若表对了但字段全无，后续可靠「召回表后回表拉全字段」补救  
4. **最后看污染**：`forbidden` 或明显无关表是否分数很高、甚至排在正确表前面  

可选：点 **生成 M-Schema**，看召回结果最终会不会进 prompt——这是「召回是否够用」的第二视角，但仍以表/字段命中为准。

### 3.2 批量指标怎么读

对正例题（不含负例）计算：

| 指标 | 定义 | 怎么用 |
|------|------|--------|
| **Table Hit@K** | 所有 `must_tables` 都出现在 Top-K | **主指标**；看 @5/@10/@15/@30 |
| **Any-Table Hit@K** | 至少一个 must 表命中 | 诊断用；高而 Table Hit 低 → 多表题弱 |
| **Column Hit@K** | 所有 `must_columns` 都在 Top-K | MVP 可放宽；表达标后再盯 |
| **Table MRR** | 首个正确表排名的倒数均值 | 看排序质量，不只看「有没有」 |
| **Forbidden@K** | Top-K 含 forbidden 表的题目占比 | 易混淆是否严重 |

**建议汇总表模板：**

| 切片 | 题数 | Table@5 | Table@10 | Table@15 | Col@15 | MRR | Forbidden@10 |
|------|------|---------|----------|----------|--------|-----|--------------|
| 全部正例 | 44 | | | | | | |
| 单表 | 12 | | | | | | |
| 易混淆 | 8 | | | | | | |
| 多表 | 10 | | | | | | |
| 同义词 | 8 | | | | | | |
| 指标 | 6 | | | | | | |

**读数经验：**

| 现象 | 含义 | 优先动作 |
|------|------|----------|
| @10 达标、@5 很差 | 能召到但排不进前几 | 加权 / rerank / 压缩噪声，而不是盲目加大 K |
| @30 才达标、@10 不行 | 靠堆 K 硬凑 | prompt 装不下；要提精度，不是加 K |
| 单表高、多表低 | 只召到一张 | 提 K 或启用 JOIN 扩展后再评 |
| 易混淆 Forbidden 高 | 近义表抢分 | 描述写清边界；监控 forbidden |
| 同义词切片低 | 口语/别名未进向量文本 | 补 synonym，或把别名写入 embed 文本 |
| 表高、字段低 | 表语义够、列文本弱 | 回表拉全字段进 M-Schema；或加强列描述 |

### 3.3 失败 case 怎么归类

每道失败题打一个主因标签：

| 标签 | 含义 | 典型改法 |
|------|------|----------|
| `DESC_WEAK` | 表/字段说明空、过粗、与问法不对齐 | 补 L1 `description`，再增量 embed |
| `SYNONYM` | 业务说法未覆盖 | 加同义词；embed 文本加入别名 |
| `CONFUSION` | 近义表分数更高 | 描述写差异句；检查 forbidden |
| `MULTI_HOP` | 多表只中一张 | 提高 K；JOIN 邻表扩展 |
| `WRONG_LAYER` | 召到 APP/DWS 而非该用的 DWD（或相反） | 题标注是否合理；或 layer/type 加权 |
| `INDEX_GAP` | 未入库 / 未启用 / 过滤掉了 | 查 `is_enabled`、库范围、points |
| `LABEL_BAD` | 标注过严/过宽 | 改黄金集，不要改模型硬凑 |

失败清单建议列：

```text
id | question | must_tables | top10_tables | first_hit_rank | 标签 | 备注
```

### 3.4 达标与决策规则

1. **Table Hit@10 < 80%** → 先别推进 SQL 生成准确率；优先改元数据（E3）和同义词（E4）  
2. **Table@10 ≥ 80%，字段很差** → 召回阶段可「中表后回 L1 拉该表全字段」；字段 Hit 不作唯一卡点  
3. **Forbidden@10 很高** → 即使 Hit 达标也要治混淆，否则 SQL 容易用错表  
4. **只有加大到 K=30 才达标** → 不算健康达标；目标是 **K=10（或你们实际注入的 K）可用**  
5. **改完元数据必须复测同一黄金集** → 否则无法证明改进有效

### 3.5 负例题怎么看

负例不求「召回正确表」，而求：

- Top-K 分数整体偏低，或  
- 命中对象明显无关且不应进入 prompt  

可单独记：**乱召率** =「仍出现高分强相关错觉」的负例占比。MVP 可先定性看 case，不必强行定阈值。

## 5. 常见问题

**Q：字段没召回，但表召回了，算成功吗？**  
A：表级指标算成功。生成 SQL 前应用「命中表 → 回 L1 拉全字段」；字段 Hit 作诊断，MVP 不卡死。

**Q：必须 50 题吗？**  
A：至少 20 题也能摸底，但要覆盖单表 / 混淆 / 多表；正式对齐 PRD 建议约 50 题。

**Q：UI 测和脚本测不一致？**  
A：对齐 `limit`、是否「全部已索引库」、同一 collection / 同一索引版本。

**Q：和端到端黄金集什么关系？**  
A：本实验是召回子集。端到端还需期望 SQL / 期望结果，应另建，避免把 LLM 错误算进召回。

**Q：多久回归一次？**  
A：大批量改 description、全量重建向量、换 embedding、改检索加权之后必跑；平时可抽 10 题冒烟。
