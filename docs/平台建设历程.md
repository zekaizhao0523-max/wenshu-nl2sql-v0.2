## 2. 基础设施：数据库与原始表

### 2.1 连接 MySQL（2026-08-06）

- **业务库**：本地或内网 MySQL / `demo_business`（示例业务表）
- **元数据库**：`demo_metadata`（L1/L2 系统表，独立账号）
- **向量库**：Qdrant（独立服务，不在 MySQL 里）

明确架构分层：

```text
MySQL
  ├─ demo_business   → 原始/示例业务表
  └─ demo_metadata   → L1/L2 元数据表

Qdrant（独立）       → 向量检索索引
```

### 2.2 建立 L1 元数据表结构

- DDL：`sql/metadata_schema.sql`
- 8 张核心表：`table_meta`、`column_meta`、`table_relation`、`metric_def`、`synonym`、`kb_document`、`kb_chunk`、`vector_index_log`
- 脚本：`scripts/init_mysql_db.py`、`scripts/db_config.py`

### 2.3 批量建原始业务表

- 逐批提供 Hive DDL，转换为 MySQL 语法
- 本地存档：`sql/raw/*.sql`
- 在 `vectortest` 中建表，最终约 **31 张** 业务表（DWD/DWS/APP 等）

## 3. 元数据流水线：从脚本到 Web 平台

### 3.1 标准数据流

```text
原始库(vectortest)
    │ 扫描（只读）
    ▼
暂存区 staging_*（metadata_vector）
    │ 用户审核 / LLM 补注释
    ▼
L1 正式表 table_meta / column_meta
    │ embedding
    ▼
向量库 Qdrant
    │
    ▼
问数 Agent：自然语言 → 召回表/字段 → 生成 SQL
```

详见：`docs/架构-L1元数据-L2知识库-向量库.md`

### 3.2 正式工作流（用户确认，2026-08-07）

1. **确定数据库连接**
2. **初始化元数据表**（创建系统表 + staging）
3. **扫描原始表**（发现结构，写入暂存区）
4. **用户确认元数据**（必须有注释：DDL → LLM → 人工修改）
5. **同步元数据到 L1**

为此新增暂存表：`staging_table_meta`、`staging_column_meta`。

### 3.3 Web 平台

- **启动**：`python scripts/run_platform.py`
- **地址**：http://127.0.0.1:8765
- **技术栈**：FastAPI + 静态前端
- **核心代码**：
  - `wenshu/app.py` — API 入口
  - `wenshu/services/pipeline.py` — 流水线编排
  - `wenshu/services/metadata_staging.py` — 扫描/暂存/同步
  - `wenshu/services/connections.py` — 连接配置向导

## 5. 本地 LLM 与注释补全

### 5.1 Ollama 部署（全部在 F 盘）

- 安装路径：`F:\Ollama`
- 模型目录：`F:\Ollama\models`
- 版本：Ollama 0.32.6
- 模型：`qwen3:4b`（适配 RTX 2060 6GB）
- 配置（`.env`）：
  - `LOCAL_LLM_URL=http://127.0.0.1:11434`
  - `LOCAL_LLM_MODEL=qwen3:4b`

### 5.2 注释补全策略

| 规则 | 说明 |
|------|------|
| 扫描不自动 LLM | 补全在「元数据编辑」步骤按需触发 |
| 扫描不写 description | 源库 COMMENT 只读存入 `hive_comment` |
| 不改源表 | 所有操作仅影响元数据库与向量库 |
| 分按钮 | 「AI 补全字段注释」/「AI 补全表注释」 |
| Qwen3 兼容 | 设置 `think: false`，避免 JSON 落在 thinking 字段 |

### 5.3 元数据同步页交互规则（2026-08-10）

- 取消「一键：初始化 + 扫描」
- 保存连接后**只连库**，不自动 init/scan
- **初始化**：元库已有系统表则显示已完成，不强制重做
- **扫描**：每次工作流须手动执行，重写暂存区
- 去掉底部 JSON 任务日志；四段式总进度 + 弹层分步进度

## 6. 字段说明：hive_comment / description / synonyms

| 字段 | 含义 |
|------|------|
| `hive_comment` | 源库原始 COMMENT，**只读备份**，不参与问数检索 |
| `description` | 业务元数据说明，**用户可编辑**，写入 L1 并参与向量 |
| `synonyms` | 同义词（独立表 `synonym` 或字段级 JSON） |

当前流程：扫描时 `description` 留空；用户手动填写、从 DDL 提取、或 AI 补全。

---

## 7. is_enabled 与同步策略

### 7.1 is_enabled = 0（软禁用）

**触发条件**：全库同步时，业务源库已不存在的表，且**未勾选**「硬删」。

- 元数据保留在 L1，但不参与问数、统计、向量构建
- 源库表恢复后，再次扫描 + 同步可设回 `is_enabled = 1`

### 7.2 硬删（purge_missing）

勾选「全库同步时硬删业务库已不存在的表」时，从 L1 **物理删除**表及字段元数据，并清理对应向量。

### 7.3 同步范围

支持 **全库 / 单表 / 单字段** 同步；向量库更新范围与元数据保持一致。

## 8. 运维踩坑与解决方案

| 问题 | 原因 | 处理 |
|------|------|------|
| MySQL 连接数满 (1040) | 远程库连接数限制 + 频繁建池 | `pool_size=2`；侧边栏「释放 DB 连接」 |
| 元库 1045 拒绝访问 | 账号密码错误或过期 | 连接向导第 ② 步核对 `metadata_vector` |
| 试连接成功但保存后失败 | 试连与保存凭证不一致 | 修复为试连接使用已保存配置 |
| 扫描中 Failed to fetch | 平台重启或扫描阻塞 HTTP | 按表分批提交；扫描期间勿关终端 |
| LLM 补全失败 | .env 未加载 / 代理 / 宽表超时 | 自动加载 .env、绕过代理、300s 超时、分批 |
| 表说明 AI 补全为空 | 字段已有注释时 prompt 无上下文 | 独立 `generate_table_description_only` |
| 工作流 500 | 元库连不上时未捕获异常 | `health.py` 降级返回错误信息 |

## 9. 当前标准操作流程

```text
① 连接配置
   原始库 → 元数据库 → 向量库 → 保存 → 进入元数据同步

② 元数据同步
   初始化（仅首次）→ 手动扫描 → 去编辑

③ 元数据编辑
   填写 / AI 补全表与字段说明 → 可选单表同步

④ 元数据同步
   全库或单表「同步到 L1」

⑤ 向量库同步
   全库 / 单表 / 单字段 增量或全量 embedding

⑥ 召回测试
   验证自然语言能否召回正确表/字段
```
